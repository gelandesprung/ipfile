# 飞鸽 P2P · 二维码配对交互与界面设计

> 状态：**已实现**（PC v2.0 / Android v2.0，2026-11-21；实现记录见第十节）
> 适用范围：PC 端（WinForms）、Android 端（Compose）
> 关联文档：[PROTOCOL.md](PROTOCOL.md) 协议 v2.0、[UI-DESIGN.md](../UI-DESIGN.md) 原发现式界面
> 设计原则：沿用现有浅色视觉规范；移动优先；配对与传输是两层独立确认；无障碍以 WCAG 2.2 AA 为准

---

## 一、改造目标与范围

把「UDP 广播发现」这一**发现手段**替换为「二维码扫码配对」，但**保留在线设备列表作为持久的发送入口**：扫码配对成功后，对方设备进入设备列表，后续从列表右键/长按发送，流程与原界面完全一致。

> 核心原则：二维码是「添加设备」的新手段，不是设备列表的替代品。设备列表是整个 App 的心智模型，发送入口收敛于此，必须保留。

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 发现方式 | UDP 广播 → 设备列表 | 二维码扫码 → 双向确认 → **设备列表**（列表本身不变） |
| 发送入口 | 右键/长按设备列表项 | **不变**：仍从设备列表右键/长按 |
| PC 角色 | 既可发也可收 | 既出示二维码（被动添加），也从列表主动发送 |
| 安卓-安卓 | 靠广播互发现 | 一方出示、一方扫码 → 双方各自把对方加入列表 |
| 设备信任 | 无（同网段即信任） | 双向确认 + token 校验 + 10 分钟有效期 |
| 确认层级 | 单层（接收确认） | 两层：配对确认 → 接收确认 |

**不在本次范围**：传输层 `FG_FILE` 协议改动、扫码库的具体集成方式。UDP 发现逻辑的删除见第九节整合映射。这些属于工程实现，见第六节代码落点。

## 三、交互流程

### 3.1 端到端时序

1. **展示方**（PC 或手机 A）点击唯一的「添加设备」入口 → 展开配对面板/进入配对页 → 此刻才生成二维码：内容含 `IPv6 + TCP 端口 + 设备名 + token`，从这一刻起算 10 分钟有效期。默认态无二维码。
2. **扫码方**（手机 B）扫码 → 解析地址 → **本机确认**「确认连接到这台设备？」→ 用户点确认。
3. 扫码方发 `FG_HELLO|1|token|扫码方名_b64|扫码方端口`，等待应答。
4. 展示方校验 token 未过期、未使用 → **弹窗确认**「设备请求配对」→ 用户点「允许配对」。
5. 展示方回 `FG_HELLO_ACK|OK`，ACK 中带回展示方的 `IPv6 + 端口 + 设备名`（扫码方能据此入列）。
6. **双方各自把对方写入设备列表**（见 3.4）：扫码方用二维码解析出的地址，展示方用 HELLO 里的地址；新设备标「刚配对」。
7. 配对面板**自动收起**（回到只有一个入口的默认态），界面回到设备列表，新设备高亮标「刚配对」。**后续从列表右键/长按设备 → 「发送文件」→ 按保存的地址连接 → `FG_FILE` + 字节流 → 展示方二次确认接收 → 落盘 → `FG_DONE`**，与原流程完全一致。

> 注：配对本身不立即发文件。配对只做「互相认识、写入列表」，发送是之后从列表主动发起的独立动作——这与原界面「设备列表 → 右键发送」的心智一致。

### 3.2 状态机（二维码生命周期）

| 状态 | 触发 | 界面表现 |
|---|---|---|
| **收起（Collapsed，默认）** | 启动 / 配对成功自动收起 / 用户点「收起」或返回 | **只显示一个「＋ 添加设备 / 扫码添加设备」入口**；二维码、倒计时、刷新、IPv6 全部隐藏；无有效 token |
| 有效（Fresh） | 点击入口展开（或展开后点刷新） | 二维码清晰、倒计时走秒、进度条递减 |
| 已配对（Paired） | 收到合法 HELLO 且用户允许 | 短暂显示「已连接 XXX」→ **约 1.5s 后自动收起回 Collapsed**，新设备在列表中高亮 |
| 即将过期（Expiring，<60s） | 倒计时进入最后 1 分钟 | 倒计时文字转琥珀色、进度条转琥珀色 |
| 已过期（Expired） | 倒计时归零 | 二维码覆盖「已过期」遮罩、按钮变「重新生成」；仍停在展开态直到用户收起 |
| 已失效（Revoked） | 用户点刷新 / **用户收起入口** | 旧码立即作废；刷新则生成新 token 回到 Fresh，收起则回到 Collapsed |

### 3.3 关键规则

- **默认收起**：启动后只有一个配对入口；只有用户点击才展开二维码与刷新，避免界面噪音和二维码长期暴露。
- **收起即失效**：点「收起」/返回主界面立即作废当前 token（与刷新同语义）；再次点击入口生成全新 token 与新一轮 10 分钟。
- **刷新即失效**：点「刷新二维码」立即作废旧 token；即使旧码在 10 分钟内，扫码也会被拒（回 `HELLO_ACK|REJECT|已失效`）。
- **token 一次性**：配对成功后标记已用，同一码不能配对第二次；展示方短暂进入 Paired 后自动收起。
- **两层确认不合并**：配对确认（设备信任）与接收确认（单个文件）是两个独立弹窗，不可跳过。
- **有效期宽度**：扫码方本机确认期间若 token 过期，连接时展示方校验失败并提示「二维码已过期，请让对方刷新」。
- **计时起点**：10 分钟从点击入口（生成 token）时开始，而非 App 启动时；收起期间不计时。

### 3.4 设备入列与在线状态（已定案：A 会话内常驻）

配对成功后双方都要把对方加入设备列表。「在线」判定经确认采用 **A 方案（会话内常驻）**，不引入心跳协议、不做持久化。

| 方案 | 机制 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A 会话内常驻** | 配对即入列，App 运行期都算在线 | 最简单、零开销 | 对方关 App 看不到；重启列表清空 | ✅ **采用** |
| B 定时保活 | 配对后维持心跳，超时判离线 | 在线状态真实 | 要新增心跳协议，与「取消发现层」冲突 | ❌ 不采用 |
| C 持久化设备 | 配对设备存本地，重启仍在 | 免重复扫码 | IPv6 地址会变，需失效重扫机制 | ❌ 不采用 |

**定案行为**：

- **配对成功 → 双方各自把对方 `Peer` 写入内存设备列表**，标「刚配对」并高亮；整个 App 运行期内视为在线，绿色在线点仅表示"本次会话内配对过"，不反映对方进程是否还活着。
- **不持久化**：`Peer` 只存内存，App 重启后列表清空，需重新扫码配对；`AppConfig` 不新增设备字段，不写本地 config/SharedPreferences/DataStore。
- **不引入心跳**：无 `FG_PING/PONG`、无超时判离线逻辑，网络层只在发送时按需连接。
- **发送失败兜底**：从列表右键/长按发送时按内存中的地址 `ConnectAsync`；连接失败则提示「设备不可达，请让对方重新出示二维码」并提供「移除设备」，用户重新扫码后以新地址覆盖入列。
- **设备移除**：右键/长按「移除设备」从内存列表删除，会话内立即生效；重启同样清空。

主链路不变：**配对成功 → 设备入列（内存）→ 从列表发送**。

## 四、视觉规范

### 4.1 色彩（沿用工程现有色板）

| 用途 | 色值 | 说明 |
|---|---|---|
| 主色 / 强调 | `#1E6FD9`（蓝） | 按钮、链接、倒计时、二维码边框 |
| 成功 / 在线 | `#1E9E4A`（绿） | 「允许配对」「已连接」「接收完成」 |
| 失败 / 拒绝 | `#C62828`（红） | 拒绝、过期错误、失败提示 |
| 警告 / 临近过期 | `#B8860B`（琥珀） | 最后 60 秒倒计时、非阻断提示 |
| 页面背景 | `#FAFAFA` | 全局浅灰底 |
| 卡片 | `#FFFFFF` | 卡片与面板 |
| 分隔线 | `#E8EAED` | 0.5px 细边框 |
| 次要文字 | `#888888` | 辅助说明、地址（等宽） |
| 主文字 | `#1C2026` | 标题与正文 |

> 对比度核验：主文字 `#1C2026` on `#FFFFFF` ≈ 15.8:1；次要文字 `#888888` on `#FFFFFF` ≈ 3.5:1（仅用于 ≥11px 辅助文本，正文不得使用）；蓝 `#1E6FD9` on `#FFFFFF` ≈ 4.6:1，满足 AA 正文 4.5:1。语义色不单独承载信息，均配文字标签。

### 4.2 字体刻度

沿用工程字号（系统 sans：微软雅黑 / Segoe UI / Roboto）：

| 层级 | 字号 | 字重 | 用途 |
|---|---|---|---|
| 窗口标题 | 15px | 500 | 应用名 |
| 区块标题 | 14px | 500 | 「传输日志」「确认连接」 |
| 正文 | 12–13px | 400 | 说明、日志、按钮 |
| 辅助 | 11px | 400 | 时间戳、IP 地址、提示 |

IPv6 地址用等宽字体（`Consolas` / `monospace`），10px，`word-break: break-all`。

### 4.3 间距与圆角

- 8px 基线：卡片内边距 12–16px，区块间距 12–16px。
- 圆角：卡片 12px，按钮 8px，手机外框 20px。
- 边框统一 0.5px，禁用阴影堆叠（仅保留功能性的 1dp 卡片 elevation）。

### 9.3 状态如何共存

新交互引入 `PairSession`（token / CreatedAt / Used），与原有状态并存、互不覆盖：

- **PC**：token 不持久化（每次启动新会话），由 `TransferService` 持有当前 session；`MainForm` 用 `Timer` 每秒驱动倒计时 UI，**Timer 仅在配对面板展开时运行，收起/配对成功即 Stop 并清空 session**；设备列表 `Peer` **仅存内存、不持久化**（A 方案，见 3.4），App 重启即清空。
- **Android**：`AppState` 新增 `pairSession` 与 `pendingPair` 两个 `StateFlow`；`pairExpanded` 为布尔状态控制入口展开/配对页路由；`ReceiveService` 同时监听 `pending` 与 `pendingPair`；配对成功的 `Peer` 走既有 `updatePeer()` 入列（**仅内存 StateFlow，不写 DataStore/SharedPreferences**），App 进程结束即清空。
- **数据流**：点击入口 → 生成码 → 写入 session → 传输层读 session 校验 HELLO → **双方各自写入对方 Peer 到内存设备列表** → 传输完成/过期/刷新/收起时清理 session；设备列表项在 App 运行期内保留，重启随进程清空（A 方案，见 3.4）。

### 9.4 代码级复用衔接点

以下既有逻辑**原样保留**，只在配对成功后才被触发：

- 接收确认：PC `TransferService.ConfirmReceive` / Android `P2PEngine.respond()` 与 `PendingRequest`。
- 进度上报：PC `TransferService.Progress` / Android `AppState.setProgress()`。
- 日志与记录：PC `TransferFinished` / Android `AppState.addRecord()`。
- 落盘：PC `NonOverwritePath` / Android `NetUtils.createReceiveStream()`。
- 网络监听：`TcpListener` / `ServerSocket` 不变，仅在 `accept` 后多一道 `FG_HELLO` 校验。
- 设备列表：`Peer` 模型、`updatePeer()` / `_devices.Items.Add()` 入列逻辑、右键/长按发送入口**全部保留**；仅新增「移除设备」项与「刚配对」标记。

> 结论：改动集中在「替换发现手段（广播→二维码）+ 新增配对层」，设备列表、发送、传输、落盘、进度、记录全部复用，无需重写。

### 10.2 最终线上格式（以此为准）

```
二维码：      FG_QR|1|<name_b64>|<ip>|<port>|<token>          （无换行）
配对请求：    FG_HELLO|1|<token>|<name_b64>|<tcp_port>\n
配对同意：    FG_HELLO_ACK|1|OK|<name_b64>|<ip>|<tcp_port>\n
配对拒绝：    FG_HELLO_ACK|1|REJECT|<reason_b64>\n
文件请求：    FG_FILE|1|<name_b64>|<size>|<filecount>\n       （与 v1 相同）
```

- `token`：16 字节密码学随机数的 32 位十六进制；只接受十六进制字符，杜绝分隔符注入。
- `FG_HELLO` 比设计稿多一个 `tcp_port`：出示方需要它才能在配对成功时把扫码方写入列表并回连。
- `FG_QR` 的 `ip` 不加方括号；连接时按 IP 字面量解析，展示时 IPv6 才加 `[]`。

### 10.3 与设计稿的差异

1. **HELLO 增加扫码方端口**：见上，属于必要补充。
2. **Android 配对页为独立页面**，不是主界面内联展开；主界面仍然只有一个「添加设备」入口，符合「默认只显示一个入口」。
3. **PC 保留手动 IP 直连**（第八节默认建议），作为手机出示码时 PC 发文件的兜底。
4. **移除设备**：PC 右键菜单、Android 长按面板均已提供。
5. **不做心跳/持久化**：按 A 方案，列表仅内存，重启清空。

### 10.4 已知限制

- 尚未在真机上做 PC ↔ Android 的端到端联调；配对与传输逻辑由 PC 侧 41 项闭环测试覆盖（含 IPv6 回环）。
- Windows 隐私扩展可能生成多个全局 IPv6；当前按「非临时地址优先」挑一个，若网络不可达需点刷新重新取地址。

## 十一、重要修正：二维码是新增能力，不替代局域网自动发现

初版实现曾把 UDP 广播发现整体删除（`DiscoveryService` 删除、Android 去掉 UDP），这是**过度删除**。二维码配对是为了解决「跨网段 / 广播被隔离」的兜底手段，同网段的自动发现必须保留——它才是零操作的主路径。

修正后的定位：

| 通道 | 定位 | 体验 |
|------|------|------|
| UDP 广播 `FG_P2P` | 主路径，同网段 | 对方一启动就自动出现在列表，无需操作 |
| 二维码配对 | 兜底，跨网段/AP 隔离 | 点「添加设备」出示/扫码，双向确认 |

两路写入**同一个设备列表**，靠 `lan` / `paired` 两个标记合并，状态列显示 `刚配对` > `已配对·在线` > `已配对` > `在线`。

关键实现点（两端一致）：

1. 广播包携带 **IPv4** 地址（广播本身基于 IPv4，带 IPv6 对端无法回连）；二维码仍优先 IPv6。
2. 同一台设备既配对过又在广播时**只保留一行**，判据是「设备名 + 端口」，且只在同名已配对设备恰好一台时合并——避免两台同型号手机被错误并成一行。
3. 广播 `BYE` / 12 秒超时：配对设备保留并降级为 `已配对`；纯广播设备删行。
4. 配对设备不参与超时清理（不依赖心跳），符合 A 方案。
5. 合并时保留**配对时的地址**（IPv6 优先），广播只用于更新在线状态。

界面改动：左栏标题回到「设备」；「＋ 扫码添加设备」仍是唯一配对入口（默认收起）；右键菜单恢复「刷新设备」；空状态文案改为「同网段设备会自动出现；跨网段请点上方『扫码添加设备』」。
