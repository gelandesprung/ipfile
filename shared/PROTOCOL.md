# 数据线 通信协议 v2.1

两端（PC / Android）必须严格遵守本协议，否则无法互通。协议刻意设计得极简，只用标准 socket，不加密、不压缩、无依赖。

**v2.1 = 两条并行的设备发现通道**：

| 通道 | 用途 | 报文 |
|------|------|------|
| **UDP 广播发现** | 同一网段自动发现，无需任何操作 | `FG_P2P` |
| **二维码配对** | 跨网段 / 广播被隔离时的手动添加，双向确认 | `FG_QR` + `FG_HELLO` + `FG_HELLO_ACK` |

两条通道**各自独立、可同时工作**，发现结果写进同一个设备列表。文件传输格式自 v1 起未变。

> 报文的版本字段始终为 `1`，v2.1 只是在 v1 之上新增报文类型，不改动已有报文的语义。

## 1. 网络模型

- 每台设备同时扮演三种角色：
  - **广播方**：每 2 秒向局域网广播自己的设备名与地址
  - **出示方（Server）**：常驻 TCP 监听端口，展示二维码，等待扫码方连接配对
  - **扫码方（Client）**：扫描二维码，主动连接出示方完成配对
- 配对成功后双方各自把对方写入**内存设备列表**，之后任一方都可作为 TCP 客户端发文件
- 无中心服务器，纯对等（P2P）
- 默认端口：UDP `2425`（广播）、TCP `2425`（配对与传输共用）。TCP 监听使用 **IPv6 双栈**（`IPv6Any` + `IPv6Only=false`），同一端口同时接受 IPv4 与 IPv6
- 地址优先使用全局 IPv6（`2000::/3`）或唯一本地地址（`fc00::/7`），跳过 `fe80::` 链路本地地址；无 IPv6 时回退 IPv4

## 2. 局域网广播发现（UDP）

### 2.1 广播包

UTF-8 文本，单行，`\n` 结尾，发送到 `255.255.255.255:2425`；Android 端额外补发一份网段广播（如 `192.168.1.255`），覆盖路由器丢弃全局广播的情况。

```
FG_P2P|1|<name_b64>|<ip>|<tcp_port>\n
```

| 字段 | 说明 |
|------|------|
| `FG_P2P` | 魔数 |
| `1` | 协议版本 |
| `<name_b64>` | 本机设备名，UTF-8 字节再 Base64 |
| `<ip>` | 本机 **IPv4** 地址（广播本身是 IPv4，携带 IPv6 地址对方无法回连） |
| `<tcp_port>` | 本机 TCP 监听端口 |

离线上线时发送带 `|BYE` 的第 6 个字段：

```
FG_P2P|1|<name_b64>|<ip>|<tcp_port>|BYE\n
```

### 2.2 时序与超时

- 每 **2 秒**广播一次；程序启动、修改设备名、手动「刷新设备」时立即补发一次
- 收到广播即 `Added`（首次）或 `Updated`（已知设备）——**周期性广播绝不能判定为离线**，否则会出现「设备上线就消失」
- 收到 `BYE` 立即移除该设备
- **12 秒**收不到任何广播判定离线（容忍 6 次丢包）
- 广播是尽力而为通道：UDP 端口绑定失败不影响 TCP 接收与二维码配对

## 3. 二维码配对

### 3.1 二维码内容

UTF-8 文本，单行，**不带换行**：

```
FG_QR|1|<name_b64>|<ip>|<tcp_port>|<token>
```

| 字段 | 说明 |
|------|------|
| `FG_QR` | 魔数 |
| `1` | 协议版本 |
| `<name_b64>` | 出示方设备名，UTF-8 字节再 Base64 |
| `<ip>` | 出示方地址，IPv4 点分十进制或 IPv6 字面量（如 `2409:8a55::5`，**不加方括号**；链路本地地址可带 `%scope`） |
| `<tcp_port>` | 出示方 TCP 监听端口（默认 2425） |
| `<token>` | 32 位十六进制随机数（16 字节密码学随机），一次性配对凭证 |

扫码方只接受 IP 字面量，不得对二维码里的 `ip` 做 DNS 解析。

### 3.2 生命周期

- **展开才生成**：出示方默认只显示一个「添加设备」入口；用户点击后才生成 token 与二维码，**10 分钟有效期从这一刻起算**
- **刷新即失效**：点「刷新二维码」立即作废旧 token 并生成新码
- **收起即失效**：收起面板 / 退出配对页立即作废旧 token
- **一次性**：配对成功后 token 标记已用，同一码不能配对第二次
- **过期**：超过 10 分钟未配对，服务端拒绝并提示「二维码已过期」

### 3.3 配对请求（扫码方 → 出示方）

扫码方在**本机用户确认对方身份**后，建立 TCP 连接并发送：

```
FG_HELLO|1|<token>|<name_b64>|<tcp_port>\n
```

| 字段 | 说明 |
|------|------|
| `FG_HELLO` | 魔数 |
| `1` | 协议版本 |
| `<token>` | 二维码中的 token |
| `<name_b64>` | 扫码方设备名，UTF-8 → Base64 |
| `<tcp_port>` | 扫码方 TCP 监听端口（供出示方入列后回连，默认 2425） |

### 3.4 配对应答（出示方 → 扫码方）

同意：

```
FG_HELLO_ACK|1|OK|<name_b64>|<ip>|<tcp_port>\n
```

拒绝：

```
FG_HELLO_ACK|1|REJECT|<reason_b64>\n
```

- `OK` 必须带回出示方的设备名、地址与端口，扫码方据此把对方写入设备列表
- 常见拒绝原因：`未在等待配对，请让对方刷新二维码`、`该二维码已被使用，请刷新后重试`、`二维码已过期，请让对方刷新`、`配对码不正确，请重新扫码`、`对方拒绝配对`
- 配对连接是**短连接**：应答后立即关闭，不承载文件数据

### 3.5 双向确认与超时

1. 扫码方扫到码 → 本机弹框显示对方设备名与地址 → 用户确认后才发 `FG_HELLO`
2. 出示方校验 token（存在、未用、未过期、匹配）→ 本机弹框显示扫码方设备名与地址 → 用户允许才回 `OK`
3. 出示方等待本机确认最长 **30 秒**，超时按拒绝处理并通知扫码方
4. 扫码方等待应答最长 **15 秒**

配对确认与「是否接收文件」是**两层独立确认**，不可合并、不可跳过。

### 3.6 配对设备的生命周期（会话内常驻）

- 配对成功后双方各自把对方写入内存设备列表，标「刚配对」（约 5 秒后恢复普通状态）
- **不持久化**：App 重启 / 进程结束即清空，需重新配对
- 配对设备**不依赖心跳**：它靠二维码建立，地址在配对握手时已确认，因此不参与广播超时清理
- 发送失败（连接超时 / 不可达）时提示「设备不可达，请让对方重新出示二维码」

## 4. 设备列表：两路来源合并规则

这是两条发现通道共存时唯一容易出错的地方，必须实现一致：

1. 列表项带两个来源标记：`lan`（广播发现中）、`paired`（配对过）。
2. 状态列显示：`刚配对` > `已配对·在线` > `已配对` > `在线`。
3. **同一台设备既配对过、又在广播时，必须合并成一行**：
   - 判据：设备名（去空格、忽略大小写）与 TCP 端口都相同
   - 只有当同名的已配对设备**恰好一台**时才合并（两台同型号手机默认同名，不能被错误并成一行）
   - 合并后保留**配对时的地址**（IPv6 优先），广播只用来更新在线状态
4. 广播 `BYE` / 超时：`paired` 为真则保留该行、状态降为 `已配对`；纯广播来源则删行。
5. 用户手动移除：`paired` 项需要重新配对才能回来；纯广播项下一轮广播会重新出现（界面需说明这一点）。

## 5. 文件传输（TCP）

### 5.1 连接与握手

- 发送方作为 TCP 客户端，连接设备列表中保存的 `<ip>:<tcp_port>`（IPv6 直接使用字面量，不加方括号）
- 连接建立后，发送方**先发一个请求头**（UTF-8 文本，单行，`\n` 结尾）：

```
FG_FILE|1|<name_b64>|<size>|<filecount>\n
```

| 字段 | 说明 |
|------|------|
| `FG_FILE` | 魔数 |
| `1` | 版本 |
| `<name_b64>` | 文件名（含扩展名），UTF-8 → Base64 |
| `<size>` | 文件总字节数（十进制整数） |
| `<filecount>` | 本次发送的文件个数（本协议一条连接只发 1 个文件，固定为 1，预留扩展） |

### 5.2 接收方应答

接收方读取请求头后，**先向用户确认是否接收**（PC 弹确认框、Android 弹对话框或通知按钮）：

- 同意并准备接收：`FG_ACK|1|OK\n`
- 拒绝（用户点了拒绝、超时未操作、空间不足等）：`FG_ACK|1|REJECT|<reason_b64>\n`

确认窗口为 **60 秒**：超时未操作视为拒绝，回 `REJECT`（`reason` 为「对方拒绝接收」），
发送方据此立即得到「被拒绝」的结果，不会一直等下去。

> 接收方必须**在用户同意之后**才创建目标文件（或 `.part` 临时文件），
> 避免被拒绝的传输在磁盘上留下空文件。

### 5.3 数据传输

- 发送方**收到 OK 后**才开始发送文件原始字节流（裸字节，不做任何编码）。
- 发送方按流式分块发送（如 64KB/块），不做整体内存加载，支持 1GB 以内文件。
- 接收方按 `<size>` 精确读取字节，写入到「接收目录 / 文件名」。
- 若目标文件已存在：自动改名为 `文件名 (1).扩展名`、`(2)` …，不覆盖。
- 用户在确认框里指定了保存位置时，写入该位置（此时允许覆盖，因为保存对话框已让用户确认过）。

### 5.4 完成确认

- 接收方收齐 `<size>` 字节、**文件落到最终位置之后**，才回复：`FG_DONE|1|<received_size>\n`
- 发送方读取 DONE，校验 `received_size == size`，一致则本次传输成功，关闭连接。
- 顺序很重要：先落盘再回 DONE，这样发送方看到「完成」时文件确实已经在对方磁盘上。

### 5.5 超时与中断

- 配对握手：出示方等本机确认 30 秒，扫码方等应答 15 秒。
- 文件握手（等 ACK）：接收方最多等 60 秒确认；发送方等 90 秒（覆盖接收方确认窗口 + 网络延迟）。
- 数据传输阶段：60 秒无数据进展视为失败。
- 任一方异常断开：另一方关闭连接、清理临时文件（接收方写入时用 `.part` 临时文件名，收齐后重命名，避免残留半截文件）。

## 6. 接收目录

- PC 端：程序目录下的 `received/`
- Android 端：公共 Download 目录下的 `数据线收件/`

## 7. 设计取舍说明

- 用 Base64 编码设备名/文件名：规避中文、空格、分隔符 `|` 带来的解析歧义。
- 广播与二维码并存而不是二选一：广播覆盖「同网段零操作」这个最高频场景，二维码解决「跨网段 / 广播被 AP 隔离」的兜底；两者写入同一列表，用户不需要知道背后走的是哪条通道。
- 广播包携带 IPv4：广播本身基于 IPv4，携带 IPv6 地址对端无法回连。
- 二维码替代不了广播、广播也替代不了二维码：前者是零操作体验，后者能跨网段。
- token 一次性 + 10 分钟 + 收起/刷新即失效：降低二维码被截图后长期滥用的风险。
- 配对设备只存内存：不引入心跳与持久化，换取实现简单；地址变化时重新配对即可。
- 一次连接只传一个文件：逻辑简单，失败重传粒度小；多文件可建立多个连接。
- 无加密：局域网可信环境，符合需求。
